## 1. Milestone A — zombify/cure PDC bridge

**Implemented as designed**, with two caveats already flagged (correctly) in
`ImplementationPlan.md` §11.1 as unverified, plus one contributing factor from the original QA
report that was never in scope for this milestone and remains completely untouched.

- `EntityListener.java`'s `onTransform` correctly filters to `INFECTION`/`CURED` only, correctly
  extracts both sides as `LivingEntity`, and delegates to `LobotomizeStorage.bridgeRestockState`.
- `bridgeRestockState` copies all four keys (`lastRestock`, `isLobotomized`,
  `lastRestockCheckDayTime`, `lastRestockPassId`) via a presence-guarded `copyIfPresent` helper —
  matches decisions A2/A3 exactly, no key missed, no unguarded overwrite.
- The A4 sentinel change (`0L` → `-1L` default, guard `>0L` → `>=0L`) was verified to be a
  near-total no-op in practice: the two behave identically for every `lastRestockCheckDayTime`
  value except exactly `0`. This matches what `ImplementationPlan.md` itself already admits — A4
  is defense-in-depth, not the actual fix — and no caller of `shouldRestock`/`allowedToRestock`
  depends on the old behavior, so nothing regressed here.
- `EntityTransformBridgeTest.java` fires `EntityTransformEvent` through a real, plugin-loaded,
  `registerEvents`-based listener dispatch (via `server.getPluginManager().callEvent(...)`), not a
  direct method call — meaningfully stronger than testing the private logic in isolation. **It
  does not and cannot validate** two things the fix's correctness ultimately depends on:
  1. That real vanilla infection/curing actually fires `EntityTransformEvent` with these entity
     types the way assumed (a MockBukkit limitation the original plan and QA report both already
     flagged as requiring manual verification).
  2. **Event-ordering assumption A5** — whether `EntityTransformEvent` reliably fires before the
     resulting entity's `EntityAddToWorldEvent`. This remains genuinely unverified; no defensive
     code exists for the case where ordering is wrong. Practical risk is lower than it sounds,
     though: `lastRestockPassId`/`lastRestockCheckDayTime` are only ever *read* by the villager's
     own periodic `EntityScheduler` task (`check-interval`/`inactive-check-interval`, default 150
     ticks ≈ 7.5s later), so even a worst-case ordering problem has a multi-second buffer before it
     could matter — but this is reasoning about the code, not a substitute for the manual
     `/runServer` pass both documents already call out as outstanding.
- **Not addressed by this milestone, and still fully open**: the original QA report's secondary
  contributing factor — a villager that physically wanders away from its job site while it's a
  hostile (non-lobotomized) zombie, then can't path back once cured and re-lobotomized, so
  `VillagerUtils.isJobSiteNearby` keeps failing regardless of PDC state. No code change was
  attempted for this in Milestone A (correctly, per the plan's scoping — it's an environmental
  interaction, not a data-loss bug), but it means "zombify/cure breaks restocking" can still
  reproduce in-game via this path even with the PDC bridge fully working. Milestone C's new "Job
  site nearby" debug field at least makes this diagnosable now, but doesn't fix it.

## 2. Milestone B — `passId` stability across `times` edits

**Implemented correctly and this is the strongest of the three fixes.** Independently
hand-recomputed the exact regression scenario from the QA report (schedule shrinks from 3 entries
to 1 across a reload):

- Old formula: day 0, all 3 points crossed → `0*3+3 = 3`. Day 1, first crossing under the
  shrunk 1-entry schedule → `1*1+1 = 2`. `2 > 3` is false → **confirmed stall**, exactly the
  reported bug.
- New formula: day 0's last crossing → `0 + 7000 + 1 = 7001`. Day 1's crossing → `24000 + 2000 + 1
  = 26001`. `26001 > 7001` → **fires correctly**.

The fix is also broader than it was scoped: since `passId` no longer references `size()`/
`ticks.length` anywhere, it's stable against *any* edit to `times` — reordering, changing a time's
value, or changing the count — not just the count-change case the QA report specifically found.

One correction to `ImplementationPlan.md` §11.2 itself: it describes the new contract as "a later
call for a larger `fullTime` never returns a smaller value." That's not strictly true —
`passId` intentionally dips back to `0` at the start of each new day until that day's first point
is crossed (this is even exercised by `RestockScheduleTest.passIdAtDayRolloverDoesNotExceedPrevious...`
itself). The property that actually holds and that the code relies on is narrower: a stored value
from an actual prior restock is always eventually exceeded once a real new crossing happens,
which is all `refreshTrades`' `currentPassId > lastRestockPassId` comparison needs. This doesn't
indicate a functional bug — traced through the actual usage and confirmed it never produces a
wrong outcome — but the plan's doc comment overstates the guarantee and should be tightened.

Both new tests are genuine regression tests, not tautological: `RestockScheduleTest`'s
`passIdComparisonRemainsValidWhenScheduleSizeChangesAcrossReload` was hand-checked to fail if run
against the old formula, and `RestockScheduleEndToEndTest`'s
`restockKeepsWorkingAfterTimesListShrinksAcrossReload` exercises the fix through a real
`plugin.reloadPluginState()` call — the actual production code path, not a shortcut.

## 3. Milestone C — documentation and diagnostics

**The `/lobotomy debug` diagnostics are implemented correctly** — "Job site nearby", "Restocks
today: n/cap", and (schedule mode) "Last restock pass id" all read the intended data with no
wrong-key or wrong-cap issues.

**The config.yml/README.md comment fix has a real structural gap that `ImplementationPlan.md`
§11.3 does not currently disclose.** Verified directly in code, not just inferred:

- `ConfigMigrator.CURRENT_CONFIG_VERSION` is still `7` (`ConfigMigrator.java:23`) — unchanged by
  this milestone, as intended (it's a comment-only edit, not a schema change).
- `ConfigMigrator.migrate()` early-returns with **zero merge work** whenever
  `existingConfig.getInt("config-version", 0) == CURRENT_CONFIG_VERSION`
  (`ConfigMigrator.java:53-56`) — an already-current config file is left completely untouched on
  plugin update.
- Even if that guard weren't there, `CommentPreservingYamlMigrator`'s merge logic explicitly
  **prefers the user's existing comment over the shipped default's** for any key/section already
  present in the user's file (`CommentPreservingYamlMigrator.java:93-101`: `comment =
  existingComments.get(keyPath); if (comment == null) { comment = defaultComments.get(keyPath);
  ... }`) — confirmed as deliberate, tested behavior via the existing
  `CommentPreservingYamlMigratorTest.preservesNestedUserCommentsDuringMerge` test.

**Net effect: the new "`mode` must be `\"schedule\"`" warning comment will never reach any server
that already has a config-version-7 `config.yml` — which, by definition, includes every server
that could have hit the confusion this fix targets, including the testing department's own
server.** Only a brand-new install (or a config manually deleted/regenerated) picks up the updated
comment. The README.md update is unaffected by this (READMEs aren't merged into anyone's live
config) and does reach anyone who re-reads it, but the in-config warning — the more likely thing
an admin actually looks at while editing `restock-schedule` — effectively does not ship to existing
installs via the normal update path.

This isn't a defect in the code that was written; it's a limitation of *how* the fix was delivered
(a config comment) given this plugin's existing, intentional "don't clobber the admin's own
comments" migration policy. It should be called a known limitation rather than implied as solved.

## 5. Test coverage: what's automated vs. manual-only

- **Bug #2 (passId)**: fully covered at both the pure-unit and real end-to-end
  (`reloadPluginState()`) level. No manual-only gap.
- **Bug #1 (zombify/cure)**: the PDC-bridging mechanism is tested; the event-ordering assumption
  (A5), the underlying premise that vanilla actually preserves `restocksToday`/experience/level
  across a real infection/cure round trip, and the job-site-drift contributing factor are all
  untested by anything in this suite and require the manual `/runServer` pass both documents
  already list as outstanding.
- **Bug #3 (mode/3-restocks confusion)**: the cap/opportunity logic for an N-entry schedule is
  well covered at the unit level; no E2E test currently drives three separate, sequential,
  individually-triggered restocks across one day for one villager (existing E2E tests use a
  1-point schedule, a 2-point schedule collapsed via one catch-up jump, or check a 3-point schedule
  only after all three already fired in one jump). Minor coverage gap, not a known bug — the
  per-point logic is identical regardless of count — but worth naming for anyone adding schedule
  tests next.

## 6. Recommendations

1. **Before closing bugs #1 and #3 in the tracker**, complete the manual `/runServer` pass already
   listed as outstanding in `ImplementationPlan.md` — specifically: a real zombify→cure round
   trip on a villager already at its daily cap, and confirmation that `EntityTransformEvent`
   actually fires (and in the expected order) for both hops.
2. **Decide how to actually get the clarified config comment in front of already-migrated
   servers** — options include a `config-version` bump specifically to force the comment refresh
   (even with no schema change), a release-notes/CHANGELOG callout, or accepting README.md as the
   sole channel and saying so explicitly rather than implying the config.yml edit covers it.
3. **Consider whether the job-site-drift contributing factor to bug #1 warrants its own follow-up
   milestone** — it's now diagnosable via the new debug field but still unfixed; at minimum,
   document it as a known limitation in README.md alongside the other schedule-mode notes.
4. **Tighten `ImplementationPlan.md` §11.2's `passId` contract description** — replace "never
   returns a smaller value for a larger `fullTime`" with the narrower, actually-true property
   (a stored crossing is always eventually exceeded by a later real crossing), so the documented
   guarantee matches what the code and its own tests actually establish.
