# QA Report — Tick-Scheduled Villager Restocks (`restock-schedule.mode: schedule`)

**Date:** 2026-08-24
**Scope:** Feature as specified in `Features/Feature_scheduled_restock.md`, implemented per
`ImplementationPlan.md`, landed in commits `466239b`, `e71625b`, `345bfcc`, `8caf6aa`.
**Reviewed against:** current `main` sources (`LobotomizeStorage.java`, `VillagerUtils.java`,
`policy/RestockSchedule.java`, `EntityListener.java`, `LobotomizeCommand.java`, `config.yml`,
and the existing unit/MockBukkit test suite). This is a static/code-level review — no live
`runServer` session was driven for this report, so item severities are marked accordingly.

---

## Summary of findings

| # | Issue reported by testers | Verdict | Severity |
|---|---|---|---|
| 1 | Zombified → healed villagers don't restock/level after re-entering lobotomized state | **Real implementation gap**, confirmed by code inspection | High |
| 2 | Non-zombified villagers show restock inconsistencies after a server restart | **Real implementation gap**, confirmed by code inspection (root cause differs from testers' framing — see below) | High |
| 3 | Unclear if 3 restocks/day (per the example `times` config) actually works | **Works as designed when configured correctly** — the confusion is most likely explained by finding #2's `mode` default, not a bug in the 3-times logic itself | Clarification, not a bug |

Both #1 and #2 are gaps the implementation plan did not anticipate — they aren't called out
anywhere in `Feature_scheduled_restock.md`'s "Open Questions" or `ImplementationPlan.md`'s
"Resolved Design Decisions", and there is no test coverage for either scenario. Recommend fixing
both before calling this feature done.

## 1. Zombified → healed villagers stop restocking/leveling

### What the code does today

`policy.RestockSchedule` gates restocks on `passId(fullTime) > lastRestockPassId`, where
`lastRestockPassId` is stored in the villager's **`PersistentDataContainer`**
(`LobotomizeStorage.java:723-725,777`). The lobotomization marker itself (`isLobotomized`,
used by `addVillager()` to decide whether to immediately re-lobotomize a re-added villager,
`LobotomizeStorage.java:280-306`) is *also* a PDC value. Restocking additionally requires
`VillagerUtils.isJobSiteNearby(villager)` to be true (`LobotomizeStorage.java:758`), and leveling
requires `villager.getVillagerLevel()` to be behind `getVillagerExperience()`
(`VillagerUtils.java:115-130`, used at `LobotomizeStorage.java:739-741`).

Villager → Zombie Villager infection and Zombie Villager → Villager curing are both **entity
replacements**, not in-place mutations: Bukkit fires `EntityRemoveFromWorldEvent` for the old
entity and `EntityAddToWorldEvent` for a brand-new entity object with a new identity. This
plugin's `EntityListener` (`EntityListener.java:66-85`) already relies on exactly those two
events for its normal add/remove bookkeeping, so both fire correctly around a zombify/cure
cycle — the villager *is* re-tracked. The problem is what data does and does not survive onto the
new entity:

- Vanilla's zombify/cure conversion (`Zombie`/`ZombieVillager` NBT copy routine) is documented and
  generally understood to carry over **villager-specific vanilla data** — profession, villager
  type, trading experience/level, and gossip — but does **not** carry over a plugin's custom
  `PersistentDataContainer` entries unless a listener explicitly copies them across the
  transformation. Nothing in this codebase listens for `EntityTransformEvent`
  (`grep -rn "EntityTransformEvent" src/main/java` returns no results) to bridge the two entity
  instances.
- That means **`isLobotomized`, `lastRestockPassId`, `lastRestockCheckDayTime`, and `lastRestock`
  are all reset to "never seen" on the freshly-cured entity**, while `villager.getRestocksToday()`,
  `getVillagerExperience()`, and `getVillagerLevel()` are vanilla-native fields that plausibly *do*
  survive the round trip (this half of the claim should be confirmed in-game per the action item
  below — see "What needs verification").

If `restocksToday` does carry over already at/near the mode's daily cap (2 for `interval`, or
`restockSchedule.size()` for `schedule` — e.g. 3, from repeated legitimate use earlier that day)
while `lastRestockCheckDayTime` resets to `0`, the day-rollover check in
`VillagerUtils.shouldRestock` (`VillagerUtils.java:216-233`) cannot fire:

```java
if (lastRestockCheckDayTime > 0L) {   // false on the very first post-cure check — PDC was reset
    ...
    villager.setRestocksToday(0);      // never reached
}
pdc.set(lastRestockCheckDayTimeKey, ..., fullTime);   // now non-zero going forward
```

Because the guard is `lastRestockCheckDayTime > 0L` rather than "has never been checked", the
missed rollover on the *first* post-cure check is never retroactively applied — the counter isn't
reset until a genuine day boundary is crossed **after** that first check re-seeds the timestamp.
Until then, `allowedToRestock` (`VillagerUtils.java:189-191`) keeps returning `false`, and the
villager is effectively stuck at whatever `restocksToday` count it carried over, for up to a full
extra in-game day. This matches the tester report precisely: villager comes back, gets
re-lobotomized by the normal `processVillager` active/inactive re-evaluation
(`LobotomizeStorage.java:558-620`, unrelated to this bug and working correctly), but restocking
stays silently dead.

Leveling is gated by the **same** daytime + job-site-nearby checks as restocking
(`LobotomizeStorage.java:750-763`, explicitly commented "Both restocking and leveling require it
to be day ... and a job site nearby"). A second, independent contributing factor for the
leveling symptom specifically: while a villager is a hostile `ZombieVillager`, it is not tracked
by this plugin at all and is free to wander (it is not subject to `NoAI`/lobotomization the way a
`Villager` is), so by the time it's cured it may no longer be within the 3×3×3
`isJobSiteNearby` box around its workstation (`VillagerUtils.java:87-109`). If it lands back in
the "active" (non-lobotomized, AI-on) state for even one `check-interval` tick before being
re-lobotomized (see next paragraph), normal villager AI might walk it back — but if it's
re-lobotomized before finding its way back, or the hall design doesn't allow it to path back at
all, it is permanently stuck away from its job site, and *both* restocking and leveling stall for
a structural reason unrelated to the PDC issue above.

There is a related, secondary wrinkle worth flagging: because `isLobotomized` PDC is lost on the
new entity, `addVillager()` (`LobotomizeStorage.java:275-307`) treats the freshly-cured villager
as brand new and calls `setActive(villager)` — i.e. for one `check-interval` window it is *not*
lobotomized, before the periodic re-evaluation puts it back to inactive
(`LobotomizeStorage.java:561-620`). Functionally this self-heals (matches the testers' "being in
lobotomized state again" observation) and is not itself a bug, but it does mean any `NoAI` state
the entity happened to already carry (a base `Mob` NBT field that plausibly *does* survive the
transform, unlike the plugin's PDC) can be briefly out of sync with which Java `Set` the villager
lives in. This is cosmetic/timing-only, not the cause of the restock/level stall, but is worth the
dev team's awareness since it's the same "vanilla-NBT vs. plugin-PDC" split causing finding's root
cause.

### Verdict

**This is a bug**, not intended behavior. It is not called out in the feature request or
implementation plan, and there is no `EntityTransformEvent` handling or test coverage for it —
`RestockScheduleEndToEndTest.java` and `LobotomizeStorageScheduleTest.java` never reference
zombification (`grep -n "Zombie" src/test/.../RestockScheduleEndToEndTest.java` → no matches). It
reproduces under **both** `mode: interval` and `mode: schedule`, since both rely on the same
PDC-keyed bookkeeping (`lastRestock`/`lastRestockCheckDayTime` for interval,
`lastRestockPassId`/`lastRestockCheckDayTime` for schedule) — it is a pre-existing gap surfaced
more visibly by the new feature's testing pass, not something the schedule feature introduced on
its own.

### Suggested fix

Add an `EntityTransformEvent` listener in `EntityListener` for `TransformReason.INFECTION` and
`TransformReason.CURED`. On `CURED` (`ZombieVillager` → `Villager`), copy `isLobotomized`,
`lastRestockPassId`, `lastRestockCheckDayTime`, and `lastRestock` from
`event.getEntity().getPersistentDataContainer()` onto
`event.getTransformedEntity().getPersistentDataContainer()` (if the transformed entity is a
`Villager` and the plugin was tracking the original) before the standard
`EntityRemoveFromWorldEvent`/`EntityAddToWorldEvent` handling runs for the pair. Separately,
consider changing `VillagerUtils.shouldRestock`'s rollover guard from `lastRestockCheckDayTime >
0L` to a sentinel that distinguishes "never checked" from "day 0" (e.g. `-1` default) so a reset
PDC value doesn't silently skip the very first rollover check regardless of *why* it was reset.

## 2. Non-zombified villagers: restock inconsistencies after a server restart

### Root cause: `RestockSchedule.passId()` bakes the schedule's size into its encoding

`RestockSchedule.passId(fullTime)` (`policy/RestockSchedule.java:169-185`) is:

```java
long day = Math.floorDiv(fullTime, TICKS_PER_DAY);
long tickOfDay = Math.floorMod(fullTime, TICKS_PER_DAY);
int crossed = /* count of configured ticks <= tickOfDay */;
return day * this.ticks.length + crossed;
```

`this.ticks.length` (i.e. `restockSchedule.size()`, the count of accepted `times` entries) is
re-derived from `plugin.getConfig().getStringList("restock-schedule.times")` every time
`LobotomizeStorage` is constructed (`LobotomizeStorage.java:109`) — which happens on **every
server start and every `/lobotomy reload`**. The villager's `lastRestockPassId` PDC value,
however, is a raw `long` written under whatever `size()` was in effect **at the time it was last
written** (`LobotomizeStorage.java:777`), and it is compared against a **freshly recomputed**
`currentPassId` using **today's** `size()` (`LobotomizeStorage.java:723,725`). Nothing invalidates
or rescales a stored `lastRestockPassId` when the schedule's entry count changes between the write
and the next read.

Concretely: suppose a test run used `times: ["08:00"]` (`size() == 1`) and a villager restocked
on day 10 after crossing 08:00, storing `lastRestockPassId = 10*1 + 1 = 11`. The server is then
restarted with the example config's three times (`size() == 3`, exactly what the tester team is
asking about). If, on restart, that villager's day/schedule state means it should legitimately be
capped again, the **next day's** first crossing computes `currentPassId = day*3 + 1`. Once
`day` is large enough that `day*3 + 1 <= 11` no longer holds it "resolves itself" naturally after
enough days — but the more damaging direction is the opposite: if the entry count instead
*decreases* (e.g. a near-duplicate `times` entry gets silently deduplicated by
`RestockSchedule.parse` — see `warnDuplicates`, `policy/RestockSchedule.java:125-137` — collapsing
`size()` from 3 to 2, or a tester trims the list while iterating on the config), a villager that
had already reached `lastRestockPassId = day*3 + 3` under the old size can end up with
`currentPassId = day*2 + 2` under the new size, which is **numerically smaller** than the stored
value. `currentPassId > lastRestockPassId` (`LobotomizeStorage.java:725`) then stays `false` for
as many in-game days as it takes for the new, smaller-multiplier sequence to catch back up and
exceed the old stored value — the villager appears to have simply stopped restocking, for a
period that scales with how large the size delta was. This is exactly the "inconsistent restocks
after a restart" symptom, and it requires no zombification and no unusual server setup — only that
the `restock-schedule.times` list was edited (added, removed, or changed count via
dedup) between two `LobotomizeStorage` constructions, which is precisely what a QA pass evaluating
"is 3 the right number of times" would naturally do.

This is confirmed as an untested gap: `RestockScheduleEndToEndTest.restockPersistsAcrossReconstructedStorageViaPdc`
(`src/test/java/.../RestockScheduleEndToEndTest.java:203-217`) reconstructs storage with the
**same** `List.of("08:00")` schedule both times — it verifies PDC persistence across a reload,
but never exercises a schedule whose `times` entry count differs between constructions.

### A second, simpler explanation the report should rule out first

`config.yml`'s shipped default has `restock-schedule.mode: "interval"` even though
`restock-schedule.times` is pre-populated with the three example entries
(`src/main/resources/config.yml:20-31`). **Populating `times` does nothing unless `mode` is
explicitly set to `"schedule"`.** If any tester's server (or a server that went through the v6→v7
migration without an explicit edit) is still on `mode: interval`, it is silently using the legacy
millisecond timer the whole time regardless of what's in `times` — which would look exactly like
"unclear if 3 restocks... are working" and could easily present as "inconsistent" behavior when
compared against expectations set by the new feature's documentation. **Before treating restart
inconsistency as the passId bug above, confirm `/lobotomy debug` on an affected villager shows the
"Next scheduled restock" line** (`LobotomizeCommand.java:186-193` only appends this line when
`isScheduleModeActive()` is true) — if that line is absent, the server is simply still in
`interval` mode.

### Verdict

**This is a bug** (the passId/size() coupling), separate from and in addition to the "did you
actually set `mode: schedule`" configuration check. Recommend fixing before calling the feature
stable — QA/testers actively exercising different `times` configurations during acceptance testing
is a completely foreseeable and even expected workflow, not an edge case.

### Suggested fix

Options, roughly in order of simplicity:
- Store the schedule's `size()` (or a hash of the sorted `ticks` array) alongside
  `lastRestockPassId` in a second PDC long, and treat a mismatch as "reset to 0 / always due" on
  read — cheapest fix, fully backward compatible (missing key defaults to "no previous size",
  treated as a mismatch).
- Redesign `passId` to encode the **absolute tick of the last crossed point**
  (`dayStart + ticks[crossedIndex]`) rather than `day * size() + crossed`. A raw absolute-tick
  comparison (`currentTickCrossed > lastStoredTickCrossed`) is stable under any `times` edit by
  construction, since it never multiplies by a config-derived count.

## 3. Does the 3-restocks-per-day example config actually work?

**Yes, by design, when configured correctly** — the daily cap in `schedule` mode is
`restockSchedule.size()` (`LobotomizeStorage.java:694`, `VillagerUtils.java:182-191`), which is
exactly the count of valid, accepted `times` entries. With the example config's three daytime
entries (`08:00`, `10:30`, `13:00`, all inside the required `06:00`–`18:00` window enforced by
`RestockSchedule.parseEntry`, `policy/RestockSchedule.java:107-119`), a villager that is
lobotomized, has a job site nearby, and has trades to restock is entitled to up to **3** restock
opportunities per in-game day, one per configured time, confirmed by
`RestockScheduleTest`/`RestockScheduleEndToEndTest` at the unit and MockBukkit-driven levels.

The testers' uncertainty almost certainly traces back to one or both of:
1. `mode` was left at (or reverted to) `"interval"` — see §2 above — in which case `times` is
   inert and none of the schedule behavior applies at all.
2. The passId/size() bug in §2, triggered by editing `times` between test runs, made restocks
   appear to stop working even with `mode: "schedule"` correctly set.

### Correct configuration to get exactly 3 restocks/day as intended

```yaml
restock-schedule:
  mode: "schedule"          # <- must be changed from the shipped default "interval"
  times:
    - "08:00"
    - "10:30"
    - "13:00"
```

Requirements/notes for this to behave as the feature intends:
- `mode` **must** be the literal string `"schedule"` — this is the part most likely to be missed,
  since the default config ships the `times` list pre-filled under `mode: "interval"`.
- All three times must fall within `06:00`–`18:00` inclusive; anything outside that window is
  dropped with a logged warning and does not count toward the cap
  (`policy/RestockSchedule.java:107-119`, only logged when `mode: schedule` is active,
  `ImplementationPlan.md` §7).
- Keep entries at least ~100 ticks (5 in-game seconds) apart — closer entries are kept but logged
  as a near-duplicate warning (`policy/RestockSchedule.java:32-33,124-137`) and, per §2 above,
  should be treated as a stability risk if edited later (changes to how many entries survive
  dedup changes `size()`).
- Each villager still needs the pre-existing gates to be satisfied at the scheduled moment for a
  restock to actually fire: lobotomized (inactive), a job site block within the 3×3×3 box around
  it (`VillagerUtils.isJobSiteNearby`), and (in the Overworld) daytime per `world.isDayTime()`
  (`LobotomizeStorage.java:750-763`) — these are unchanged from `interval` mode and are not new
  requirements introduced by this feature.
- Once `mode: schedule` is set with a stable `times` list, **avoid further edits to the `times`
  list count** on a live server with existing lobotomized villagers until the §2 fix lands — each
  edit followed by a restart/`/lobotomy reload` risks the passId mismatch described above for any
  villager that had already restocked under the previous list.

## Action items for development

1. **Fix (High):** Add `EntityTransformEvent` handling to carry `isLobotomized`,
   `lastRestockPassId`, `lastRestockCheckDayTime`, and `lastRestock` PDC values from the
   pre-transform entity to the post-transform entity on both infection and cure. Add a MockBukkit
   test simulating a zombify→cure cycle mid-lobotomization to prevent regression.
2. **Fix (High):** Decouple `RestockSchedule.passId()`'s encoding from `size()`, or store a
   size/version tag alongside `lastRestockPassId` and treat a mismatch as invalidated. Add a test
   that reconstructs `LobotomizeStorage` with a *different* `times` list (both larger and smaller)
   between two ticks and asserts restocking doesn't silently stall.
3. **Clarify (Docs):** `README.md`/`config.yml` comments should more prominently call out that
   populating `restock-schedule.times` has no effect unless `mode` is also changed to
   `"schedule"` — the current comment structure makes it easy to fill in `times` and assume that
   alone activates the feature.
4. **Verify in-game (blocked on manual testing, not code review):** Confirm empirically whether
   `villager.getRestocksToday()` / villager experience/level actually survive a vanilla
   zombify→cure round trip on the Paper version this plugin targets. This report's analysis
   assumes they do (based on documented vanilla `VillagerData` copy behavior) and that
   plugin-custom PDC does not; if that assumption is wrong in either direction, finding #1's exact
   mechanism should be revised accordingly, though the "no `EntityTransformEvent` listener exists"
   fact and its impact on `isLobotomized`/`lastRestockPassId`/`lastRestockCheckDayTime` holds
   regardless.
